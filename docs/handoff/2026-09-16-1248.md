## Problems Encountered and Decision Process

### Problem: Primary Answer and Key Session prose left a large empty right area

#### Investigation

实际计算样式显示：

- Primary Answer 容器宽 992px，正文段落因 `max-width:66ch` 只有约 528px。
- Key Session 的 `finding`、`finding-lead`、行动标题、行动说明和验证说明分别受 82ch、34ch、38ch、70ch、78ch 限制。

#### Final Decision

取消这些正文模块的窄 `max-width`，让它们使用所属模块的可用宽度；保留字号和层级差异，用字体大小而不是空白表达层级。

#### Rationale

当前报告是单一阅读流，没有对应的右栏内容。把文字固定在左侧窄栏会制造无法解释的空白，不符合用户要求的紧凑 Kami 桌面阅读节奏。

### Problem: Cache and cost metric values moved vertically when labels wrapped

#### Investigation

指标卡内部原本是普通纵向流。标签一行或两行时，数值直接跟在各自标签后面，导致同一指标组内数值的顶部不一致。

#### Final Decision

为指标卡建立两行标签轨道，并将经济指标组固定为两列；四项指标因此呈 2×2，长标签和单行标签共享同样的标签区高度。

#### Rationale

指标组的首要任务是横向比较。2×2 同时降低窄列换行压力，并保留 Kami 风格中清晰、安静的指标节奏。

### Problem: Report artifact did not reflect source changes

#### Investigation

报告是静态 HTML。修改 `src/report.ts` 后，必须执行构建并通过 compose workflow 重新生成同一路径的报告；直接查看旧标签页可能仍显示旧 DOM/CSS。

#### Final Decision

每次源码修复后执行 `npm run build`，再运行现有报告 compose 脚本，最后用桌面浏览器计算样式验证。
