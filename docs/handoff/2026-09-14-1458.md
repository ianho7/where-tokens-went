## Problems Encountered and Decision Process

### Problem 1：不同 Session 出现完全相同的 AI 解读

#### Investigation

多个 Session 的 Host Agent 文案可能在缺少 Session-specific Evidence 锚点时复用同一个通用结论；原有校验只验证结构和 Evidence ID 合法性，未检查 evidenceRead 是否实际覆盖 Finding/recommendation 引用，也未检查不同 Session 之间的核心文案重复。

#### Solutions Considered

- 接受文案：实现最小，但会把可能的生成流程错误直接展示给用户。
- 在 renderer 中强行改写或拼接 Session 名：能制造差异，但会伪造 Host Agent 解释，不符合 Evidence 边界。
- 引入模糊语义模型：覆盖面更广，但增加依赖、误判和范围。
- 在校验/组合边界做精确重复拦截，并要求 Host Agent 依据独立 Evidence 重新生成：实现小、可解释、不会强造差异。

#### Final Decision

选用最后一种：校验 evidenceRead 的最小 Turn 集合及 Evidence 覆盖；在组合时比较 observation、interpretation、recommendation.action 的标准化核心文案，完全重复的 Session 标记 unavailable，并在 Skill 中要求仅对受影响项重新读取/生成一次；若没有 Session-specific Evidence，则使用显式无强结论状态。

#### Rationale

把质量门放在结构化分析进入 renderer 之前，可以保留原始确定性轨迹，避免自动改写 AI 意图，也不需要新增抽象或依赖。

#### Future Implications

共同结论仍可能是正确的；只有完全相同的核心文案会被拦截。未来若证据显示近似套话普遍存在，再增加独立、可验证的相似度规则。

### Problem 2：组合报告标题显示 project

#### Investigation

脱敏后的 AuditResult.scope.cwd 是 <current-project>，不能用于读取本地 .git/config 或项目元数据。直接 renderer 路径已有本地项目名解析，但正确的 compose-report 路径此前只接收 sanitized AuditResult，没有接收本地解析结果，因此安全回退到 project。当前仓库只读核对到远端 where-tokens-went，包名也是 where-tokens-went，目录名为 agent-audit。

#### Solutions Considered

- 从 <current-project> 猜名字：不可验证，且会把脱敏占位符泄露进标题。
- 把项目名写入 AuditResult：会破坏脱敏数据和数据语义边界。
- 让 Host Agent 在 prose 中自行生成项目名：不可稳定校验，且把本地元数据混进 AI 文案。
- 在最终 envelope 中增加 local-only projectName，由本地解析规则提供并在 renderer 使用：隔离清晰、改动最小、可测试。

#### Final Decision

采用 local-only projectName，放在 AuditResult 外；renderer 优先使用它，否则按远端仓库名、包名/项目名、目录 basename、project 回退。Skill 文档把该字段列为最终组合的必需本地投影。

#### Rationale

既修复真实 compose-report 路径，又保持 sanitized Audit 的隐私契约和项目/时间范围边界。

#### Future Implications

所有最终报告调用方都必须遵守 envelope 约定；不传该字段时仍有安全回退，但不会保证显示真实远端/包名。

### Problem 3：确定性预览被误当成最终报告

#### Investigation

用户看到的“Host Agent 综合不可用”和“关键 Session 分析不可用”与直接 inspect --html 或缺少结构化 envelope 的路径相符。该路径没有完成 Host Agent synthesis、Key Session analysis 和最终组合校验。

#### Solutions Considered

- 继续暴露低级 Node/HTML 命令：操作看似简单，但容易产生错误的最终报告。
- 让确定性 renderer 伪造 AI 文案：会混淆事实与解释。
- 把 Skill 作为用户入口，内部先取得 Audit，再生成/校验 synthesis 和 Key Session 分析，最后只调用一次 compose-report 并打开最终 HTML：流程清晰且保持降级边界。

#### Final Decision

在 AGENTS.md 和 Codex/Claude Skill 中固化完整流程；确定性 inspect --html 只作为非最终 fallback，不再作为正常 full/report 交付路径。

#### Rationale

Host Agent 是 AI 解释的必要参与者，确定性 runtime 只负责事实、验证和安全降级；把两者分开才能解释为何某些模块可用而 AI 综合不可用。

#### Future Implications

后续报告请求必须从 $where-tokens-went 或等价自然语言 Skill 入口开始，并以最终组合 HTML 打开作为完成条件。

### Problem 4：需要增加章节层但不能重做模块

#### Investigation

需求只要求阅读顺序标记；直接重排或包裹整个 section 会改变已有视觉和可访问契约。测试需要同时确认双语文本、稳定编号、周对比有无时的 03 位置，以及原 h2 顺序。

#### Solutions Considered

- 新建通用章节框架或导航系统：范围过大，改变交互/结构。
- 使用 CSS content：不可作为真实 DOM 文本，辅助技术和测试不可靠。
- 在现有 report render 路径中增加最小 marker helper，并复用 typed localization：改动局部、语义透明、满足 Kami 视觉要求。

#### Final Decision

采用一个最小 renderSectionMarker()，在五个现有模块组前插入真实文本行；只增加 presentation CSS 和定位，不替换任何标题或模块。

#### Rationale

满足“五段式章节标记”而不引入组件系统、依赖、锚点或数据层变化。

#### Future Implications

编号固定为 01–05，即使可选周对比缺失也不重编号；新增模块应归入现有阶段，除非未来需求明确改变章节契约。
